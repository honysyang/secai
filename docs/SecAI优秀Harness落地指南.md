# SecAI 优秀 Harness 落地指南

> 目标：先把 SecAI 打造成一个**优秀的 Harness**（智能体运行平台），再谈得分。
> 核心公式：**得分 = 模型智力 × Harness 兑现率 × 确定性转化率 × 状态累积率**。
> 模型智力我们买不到更多，但后三项全部由 Harness 决定——这就是落地指南的全部内容。
> 参照系：DeepSeek Harness（dsh）的五个设计答案——单主线智能体、append-only 轨迹、动静分离前缀、PTC 批量原语、轨迹可回放。

---

## 第 0 章 总纲：Harness 五问与 SecAI 的答卷

| 问题 | 优秀 Harness 的标准 | SecAI 现状 | 落地章节 |
|---|---|---|---|
| 单/多智能体怎么选 | 单主线 + 用完即弃的临时分身 | 四常驻智能体，伪证会沿状态传递污染下游 | 第 1 章 |
| 上下文爆炸怎么办 | 三层记忆 + 代码确定性归档 + append-only | 压缩重建上下文、前缀断裂 | 第 2 章 |
| AI 惰性怎么办 | 零增量机械熔断 + 强弱模型分工 | 有零增量计数但无破局机制 | 第 3 章 |
| 成本怎么算 | 缓存命中率 ≥85%，成本公式进看板 | 命中率 0%，动态模板每轮重写前缀 | 第 4 章 |
| 效率怎么提 | 批量原语（PTC）优先，动态智能体是三闸门下的最后选项 | 一步一请示，无批量执行 | 第 5 章 |

落地顺序即章节顺序：**先稳上下文和缓存（省钱省时的根），再补惰性和效率（提分的杠杆），最后动智能体结构（最伤筋动骨，放最后）**。

## 第 1 章 智能体结构：从"四常驻"到"单主线 + 临时分身"

### 1.1 设计原则

- **智能体的数量不是能力，轨迹的质量才是。**
- 多智能体的隐性代价：前一个智能体的"伪证"（未验证结论）作为状态传递，会污染下游所有智能体，造成大量 token 消耗甚至错误结论。
- 单智能体的核心价值：**完整上下文、分析连续性、无信息传递损耗**。

### 1.2 目标架构

```
                    ┌─────────────────────────┐
                    │   调度器（代码，非AI）    │  ← 选题、预算、熔断，全部确定性
                    └───────────┬─────────────┘
                                │
                    ┌───────────▼─────────────┐
                    │  Executor（唯一常驻AI）   │  ← 持完整上下文的主线
                    │  快模型驱动，工具全集门控  │
                    └───────────┬─────────────┘
              ┌─────────────────┼──────────────────┐
              ▼                 ▼                  ▼
      ┌──────────────┐  ┌──────────────┐  ┌──────────────┐
      │ 轨迹分叉分析   │  │ 批量脚本(PTC) │  │ 临时子智能体  │
      │ 强模型,一次性  │  │ 零AI开销     │  │ 三道闸门     │
      └──────────────┘  └──────────────┘  └──────────────┘
```

### 1.3 改造步骤

**Step 1：Planner / Coach 降级为"轨迹分叉分析"（一次性调用，不常驻）**

- 现状：Planner/Coach 作为常驻 agent 参与每轮循环，它们的结论以消息形式注入 Executor——伪证污染的主通道。
- 改造：卡壳（零增量熔断触发）时，把最近 N 步轨迹导出，fork 给强模型离线分析，产出**一条**"下一步指令"写回黑板。主线不中断、不等待。
- 代码落点：`core/agents_def.py` 删除 Planner/Coach 常驻循环；新增 `runtime/fork_analyst.py`：

```python
def fork_analyze(trajectory_tail: str, blackboard: dict) -> str:
    """轨迹分叉：强模型一次性分析，返回一条下一步指令。"""
    prompt = FORK_ANALYST_STATIC  # 静态模板，一字不动
    msg = render_blackboard(blackboard) + "\n\n[最近轨迹]\n" + trajectory_tail
    return strong_pool.one_shot(prompt, msg)  # 结果由代码写入 blackboard['next_directive']
```

**Step 2：Manager / Reporter 彻底代码化**

- 调度、记账、报告生成全部是确定性逻辑，本就不该是 AI。`bench_platform/scheduler.py` 已承担大半，补齐 Reporter 的输出模板即可。

**Step 3：临时子智能体三闸门（保留但收紧）**

保留现有 subtask 机制，但必须满足三道闸门才可创建：

| 闸门 | 机械判定 | 代码落点 |
|---|---|---|
| 明确目标 | 创建时必须写死 `objective` 字段，空则拒绝 | `subtask.create()` 校验 |
| 独立预算 | `token_budget` / `turn_budget` 独占，烧完即停 | 子上下文独立计数 |
| 回收机制 | 完成即收；零增量 ≥3 轮处决；前提证伪即撤（父分支假设被推翻时级联回收） | 回收钩子 + 死路归档 |

**验收标准**：任意时刻运行中的 AI 智能体 ≤ 1（主线）+ N（带闸门的临时分身，N ≤ 2）。

## 第 2 章 上下文工程：三层记忆 + 确定性归档 + Append-only

### 2.1 三层记忆职责表

| 层 | 内容 | 写入方 | 生命周期 |
|---|---|---|---|
| 短期（session） | 当前题原始工具输出、推理过程 | 模型/工具 | 题目结束即弃 |
| 中期（黑板） | 已验证事实、flag、死路登记、hint 法令、下一步指令 | **只由代码写入** | 跨压缩存活，题目结束归档 |
| 长期（field_notes / 模板库） | 跨题经验、payload 模板、wiki 套路 | 赛后代码归档 | 永久，按需检索注入 |

### 2.2 铁律：归档用代码，不用 AI 自觉

- 含 flag 正则的输出 → 代码必存黑板（`flags_seen`），并触发提交闸门；
- 失败 payload → 代码登记死路（`dead_ends`），同分支 EV 衰减；
- hint → 代码法令化：`hint_directive` 写黑板 + 关键词方向锁 + 5 轮熔断（已有补丁，本章并入主线）；
- AI 摘要只允许写"下一步建议"这一个字段。

### 2.3 Append-only 轨迹改造（治压缩断前缀的根）

- 现状：压缩时重建上下文 → 前缀断裂 → 缓存命中率 0%。
- 改造：压缩**不删历史**，而是：
  1. 代码把压缩产物（黑板快照）作为一条新消息**追加**到尾部；
  2. 原轨迹逻辑保留（物理截断只在超长硬阈值时发生，且只截最旧的工具输出正文，保留每步结论行）。
- 代码落点：`core/task_context.py` 的 compact 流程：

```python
def compact(ctx):
    snapshot = render_blackboard(ctx.blackboard)   # 代码渲染，确定性
    ctx.messages.append({"role": "user", "content":
        "[黑板快照·压缩锚点]\n" + snapshot + "\n[下一步]\n" + ctx.blackboard.get('next_directive','继续')})
    ctx.truncate_old_tool_outputs(keep_conclusion_line=True)  # 只截正文，不删步骤
    # 禁止：重建 messages 数组、修改 system prompt
```

### 2.4 假长真短

每题独立 session（已是现状），压缩锚点保证"题内连续、题间轻装"。**不要把长任务塞进同一会话**——会话是工作记忆，黑板才是记忆。

**验收标准**：压缩前后 system prompt 与工具定义的字节 diff 为 0；压缩后黑板关键事实（flag/hint/死路）100% 在场。

## 第 3 章 AI 惰性治理：机械熔断 + 强弱分工

### 3.1 惰性的四个根因（先诊断再开药）

1. **上下文稀释**：关键指令淹没在长上下文，注意力衰减；
2. **目标信号缺失**：模型没有增量奖励，倾向输出"看起来在推进"的安全回复；
3. **无惩罚循环**：重复无增量工具调用不被制止；
4. **能力错配**：快模型在困难分支到天花板——表象是懒，实质是不会。

### 3.2 落地机制

**机制 A：零增量熔断（代码判定，不商量）**

```python
# core/hooks.py
if ctx.zero_gain_turns >= 3:
    directive = fork_analyze(tail(ctx.trajectory), ctx.blackboard)  # 第1章的分叉分析
    ctx.blackboard['next_directive'] = directive
    ctx.zero_gain_turns = 0
    ctx.escalate_model = True   # 下一个回合切强模型
```

**机制 B：强弱模型分工**

- 常规推进：快模型（V4-Flash 级）；
- 破局回合：强模型（V4-Pro 级），每题最多 N 次（N=3，计入预算）；
- 触发条件（机械）：零增量熔断、证据闭环卡住、错交 ≥3 次后。

**机制 C：证据闭环强制**

- hooks 的正则触发（LFI/SQLi/RCE/上传/反序列化/SSRF/业务逻辑）已有，补两点：
  - 收紧误报：bare "root"、"200" 不触发；要求"触发词 + 上下文窗口内有关键证据"双条件；
  - 闭环有出口：证据→提交的动作由代码提示并计数，超 2 轮未闭环升级强模型。

**机制 D：错交熔断回归修正**

- `wrong_submit_count >= 3` 会杀掉已验证的"快试模式"（bctf-13 六败后 +800）。
- 修正：`wrong_submit_count >= 6 AND zero_gain_turns >= 3` 才熔断；任何 `turn_gain > 0` 重置计数。

**验收标准**：日志中"连续 5 轮无任何信息增益"的事件数 = 0；每题强模型调用 ≤ 3 次。

## 第 4 章 成本工程：把缓存命中率当利润率管

### 4.1 定价现实

- 缓存只认**逐字节相同的前缀**；命中部分价格 ≈ 未命中的 1/10，且免全量 prefill 延迟。
- SecAI 此前命中率 0% 的根因：`EXECUTOR_TEMPLATE` 每轮动态渲染（render_situation 拼进 instructions）。
- **单场成本 ≈ Σ(未命中 token × 全价 + 命中 token × 0.1 价)**。5 小时比赛，0% 与 90% 命中率账单差近 10 倍，还附带每轮全量 prefill 的延迟——这是"解题慢"的隐性元凶。

### 4.2 动静分离改造（最高优先级的一刀）

```python
# core/agents_def.py
EXECUTOR_STATIC_TEMPLATE = """你是 Executor……（全部纪律、工具用法、输出格式一次定稿）"""
# 铁律：此字符串定稿后一字不动；任何"每轮变化"的信息禁止进入 instructions

def _wrap_input(ctx, msg):
    return render_situation(ctx) + "\n\n" + msg   # 动态内容只走 user message 尾部
```

- 工具定义同理：全量工具 schema 固定注册一次（顺序也固定），**用逻辑门控而非增删工具**控制可用性：

```python
GATED = {'progress_hint': 'has_unsolved', 'finalize_challenge': 'evidence_closed'}
def _gate(ctx, name):
    return name not in GATED or ctx.check(GATED[name])  # 禁用时报错引导，不从列表删除
```

### 4.3 渐进披露（Skills 与工具）

- Skills 不进常驻前缀；`query_skills` 先返回 TLDR（≤100 字），命中 ≥2 个触发词才注入正文；
- 每个阶段只暴露当前分支需要的工具（Minimal 模式思想）——但用门控实现，不改前缀；
- 修复 `list_tools` 空列表 bug（`_NO_PROGRESS_TOOLS` 误伤导致的死循环诱因）。

### 4.4 成本看板

- 每轮记录 `cached_tokens / prompt_tokens`；看板第一指标：缓存命中率，目标 **≥85%**；
- 记账模块输出单场成本公式拆解（未命中/命中各多少），赛后可核对。

**验收标准**：同题第 2 轮起命中率 ≥85%；无动态内容进入 instructions 的回归测试（对 system prompt 做 hash 断言）。

## 第 5 章 效率工程：批量原语优先，动态智能体兜底

### 5.1 效率分层（按杠杆率排序）

| 层级 | 手段 | 开销 | 优先级 |
|---|---|---|---|
| 单点调用慢 | 批量脚本（PTC 思想）：模型写脚本，一次拿回全部数据 | 零额外 AI 开销 | P0 |
| 分支探索 | 轨迹 fork + 强模型一次性分析 | 一次调用 | P1 |
| 结构性并行 | 3 容器槽位调度（已有） | 平台层 | 保持 |
| 动态生成智能体 | 三闸门下的临时分身（第 1 章） | 最贵 | **最后选项** |

### 5.2 批量原语落地

```python
# demo_tools.py 新增
def run_batch(script_path: str, timeout: int = 120) -> str:
    """执行模型生成的探测脚本，返回汇总输出（截断保护）。"""
    r = subprocess.run(["python3", script_path], capture_output=True, text=True, timeout=timeout)
    return _spill_output(r.stdout + r.stderr)
```

配套：

- **零 LLM 预侦察** `_first_strike(addrs)`：拿到容器地址后，代码直接跑端口/HTTP/指纹探测，结果写入第一条 user message——模型第一轮就看到战场全貌，省 3-5 轮盲探；
- **exploit_fuzz 迭代器**：payload 枚举、差异基线判别全在脚本内循环，模型只看汇总表。

### 5.3 原则复述

> 让模型写脚本编排多步探测——for 循环扫端口、批量试 payload、条件分支全在代码里——**一次执行拿回全部数据，而不是一步一请示**。模型负责思考，代码负责枚举。
> 先把批量脚本和轨迹分叉做好，80% 的"想要子智能体"的场景会自然消失；剩下 20% 才值得开子会话，且严格按三道闸门回收。

**验收标准**：常规探测类任务单轮工具往返次数 ≥5 倍提升（日志统计"模型轮次 / 有效探测动作"比值下降）。

## 第 6 章 稳定性与状态累积（底座补丁合入）

以下已在赛前补丁中验证，本章作为落地清单合入主线：

1. **槽位泄漏检测**：`leaked = [c for c in containers if c.status=="running" and c not in active]`，连续 3 次轮询机械关闭 + `close_pending` 重试队列；
2. **全局共享 ModelPool**：`fast_pool = ModelPool(preferred_name=FAST_MODEL_NAME)`，禁止每题重建（重建即前缀缓存失效 + 失败状态丢失）；
3. **墙钟预算**：`WALL_CLOCK_LIMITS = {easy:2400, medium:3600, hard:5400}` + 进度展期（`_wallclock_extended`，有增量才续命）；
4. **覆盖率加权**：`if attempts.get(code,0)==0: ev *= 3.0`——63 题中 23 题零启动是最大失分源；
5. **收尾期阈值减半**：ENDGAME_DECAY=0.6，last hour 进入"有证据就试"模式；
6. **sub_*.sqlite 清理**：子会话回收时物理删除，防状态串题。

## 第 7 章 可观测性与回放（Harness 的眼睛）

- **轨迹导出**：每题结束落盘 `trajectory_<code>.jsonl`（append-only 原样），支持赛后 replay；
- **惰性点回放**：每次零增量熔断自动导出前后各 5 步，人工/强模型复盘后沉淀为 field_notes 反例；
- **看板四指标**：缓存命中率、零增量事件数、轮次/有效动作比、单题 token 成本——每场赛后先开这四个数，再谈战术。

## 附：一句话总纲

> 智能体的数量不是能力，轨迹的质量才是；
> 上下文不是越多越好，是前缀越稳越好；
> 惰性不是态度问题，是目标信号与能力错配问题；
> 成本不是玄学，是缓存命中率的定价函数；
> 效率不是孵化更多 AI，而是让一个 AI 一轮做完更多事。
>
> **先把 Harness 修成一台确定性机器，再把模型放上去狂奔。**
