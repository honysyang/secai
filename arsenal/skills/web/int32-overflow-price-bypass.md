# 订单结算 int32 溢出绕过余额校验

## 场景特征
电商/支付类题目，后端源码可读（或可从同网段源码站下载），发现**校验段与结算段使用不同位宽整数**：
- 业务合规校验（数量、单行小计、核账总额）用 `int64` 精确计算；
- 支付网关装配段把金额累加进 `int32` 字段（注释常写"网关报文 32 位 gross 金额字段"）。

## 漏洞本质
`gross int32` 逐行累加时溢出：`gross = (Σ行小计) mod 2^32`（有符号解释）。溢出后的值再减去券面额，得到**最终待扣金额**。只要余额校验与扣款都拿这个溢出后的 `charge` 判定/扣减，就能用极小金额买下远超预算的商品。

## 攻击步骤
1. 读源码确认：校验边界（每行 qty/金额上限、总件数上限、核账上限、券面额≤总额）与结算位宽。
2. 收集商品单价（分）与优惠券面额。注意购物车模型：**同 SKU 重复加购通常覆盖数量**，每个 SKU 只能一行；行数有上限。
3. 求购物车组合使 `Σ(单价×数量) ≡ T (mod 2^32)`，其中：
   - 用有符号解释 `s = signed(Σ mod 2^32)`；
   - 目标 `charge = s - coupon ≥ 0` 且 `charge ≤ wallet`；最理想是 `charge = 0`（`s = coupon`）。
4. 若存在单价为 1 分的小额商品（如积分充值），用它做 1 分粒度微调：`p = (T - Σothers) mod 2^32 ∈ [0, qty上限]`。随机搜索 6 行大额组合 + 小额微调行即可快速命中（概率约 2e-5/样本，百万级样本足够）。
5. 每行同时满足：`qty ≤ 单行数量上限`、`单价×qty ≤ 单行金额上限`；全单 `Σqty ≤ 总件数上限`、`Σ金额 ≤ 核账上限`、行数 ≤ 上限。
6. 校验复核后逐行加购→核销券→结算→访问会员/权益页取 flag。

## 判定要点
- 溢出后 `charge` 为负会被风控拒付，须落在 `[0, wallet]`。
- 券面额不能超过核账总额（int64 audit），通常易满足。
- 溢出绕的是"金额"，不要动数量上限本身（数量校验在 int64 段是完备的）。
